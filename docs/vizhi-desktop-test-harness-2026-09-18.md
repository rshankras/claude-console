## Shortcut delivery fix and local installation

The recorded delivery failure was traced to the one-shot helper's lifetime. With the fixture
frontmost and its key window verified, immediate process exit produced no received events.
Keeping the same private-source, PID-targeted events alive for 200ms delivered both key-down
and key-up. Changing the event source was unnecessary. This is an experimentally verified
cause of the fixture failure; it does not by itself establish real ChatGPT Voice behavior.

`tools/desktop/VizhiAxBridge.swift` now retains its event source and events while servicing the
run loop for 200ms after posting, within the caller's 2500ms budget. Foreground/PID guards remain
in force. The response continues to mean requested, because the app provides no acknowledgement.
The fixture now checks three separate helper processes, exact down/up pairs, modifier flags,
the selected window, and background refusal. It records only metadata for its fixed V test key.

runtime and the installed plugin's `bin/desktop` payload. Updating the payload prevents the old

## Recommendation

Build a Desktop-specific harness with one command catalog, an automated scenario runner, and a
guided hardware checklist. The owner performs the live keypad/ChatGPT/Codex checks. The harness
prepares and records those checks so failures are reproducible and retesting is easy.

Reuse the host-independent command approach proposed in [test-architecture.md](test-architecture.md),
existing Desktop automation fakes, and the current package verifier. That earlier document is a
historical proposal spanning the terminal products; its old inventory/counts are not today's baseline.
Desktop does not need a replacement for the terminal hook test infrastructure.

## Why the existing green suite did not catch the voice problem

Current tests are strong around state transitions, argument construction, matching rules, and
failure handling. Several contract tests only check that strings exist in source. The Swift tests
execute production matching/dispatch functions against synthetic inputs; the package test compiles
the entire helper but does not exercise its live app operations.

There is no single scenario runner that exercises every production command handler and its face
through the same path as a hardware press. For example, the Context tests check face mapping, and
Workflow tests check templates and submission flags, but they do not drive every corresponding
`RunCommand` branch. An app can also change its accessible controls while all synthetic tests pass.

The harness must track three distinct outcomes: command behavior is correct in simulation,
the helper works against a controlled test app, and the installed product works in the real app.
Only the owner's live run establishes the last outcome. Physical hardware is not the only remaining
variable: app compatibility, focus, permissions, and microphone behavior also require that run.

## Automated runner

1. Use one catalog keyed by command ID, parameter, mode, profile/page/key, scenario, and expected
   outcome. Check it against the packaged profile bindings and registered command parameters.
   A new or renamed binding without coverage fails the coverage check. Optional actions belong
   in the catalog even when absent from the default profile. User-custom workflows need their
   resolved configuration recorded for a manual run.
2. Move remaining `RunCommand` decisions into small host-independent handlers that the SDK
   commands call. Extract label/icon/footer/enabled state as a face model. Test those same
   handlers; do not create an alternative test-only command implementation.
3. Inject automation, capture, clipboard, configuration, and clocks. Assert outgoing operations,
   feedback, face transitions, and repaint counts. Use temporary state/configuration and an inert
   recorder/clipboard for the default automated run.
4. Add a separate macOS fixture app with controlled buttons, controlled AppKit web-area/text-area accessibility roles, two windows, and a
   shortcut event receiver. Exercise the compiled helper against this fixture to test actual AX
   traversal, writing, focus guards, and event delivery. This requires a GUI session and the
   appropriate local permissions; report unavailable prerequisites as BLOCKED, not PASS. It does
   not inspect or operate ChatGPT and cannot prove ChatGPT's current accessibility layout.
5. Optionally run bundled Whisper against a fixed test audio file to verify inference and transcript
   handling without opening the microphone. Keep actual recording/device selection on the manual
   checklist. Missing model/runtime is reported explicitly.
6. Run package checks and report unexecuted platform/link checks separately. Record commit, dirty
   state, package/DLL/helper hashes, profile identity, OS and relevant configuration with each run.

First regression scenarios should be the failures seen in this session: available Voice with missing
AX controls; configured toggle with no readable surface; transcription succeeded but insertion
failed; clipboard recovery; no speech; existing draft; repeated press; wrong foreground app; mode
change; and Copy Answer correctly remaining unavailable.

## Guided hardware runner

Use a small local browser page with a 3×3 keypad map. Highlight one physical key and show the
preparation, one action, and expected results in both ChatGPT and on the keypad. The owner drives
the keypad and app; the page records **Pass / Fail / Blocked / Not tested**, notes and optional
owner-supplied evidence. Unsupported features are a separate capability status.

Example card:

| Field | Example |
|---|---|
| Case | `voice.toggle.start.chatgpt` |
| Location | Adaptive 3 → Conversations → row 3, column 3 |
| Prepare | ChatGPT frontmost, Voice inactive, no local dictation in progress |
| Do | Press Voice Chat once |
| Expect in app | Native Voice opens, or first-use setup appears; setup is a prerequisite before retesting start |
| Expect on key | Voice Chat / TOGGLE, with transient Requested feedback |
| Result | Owner selects Pass/Fail/Blocked and adds a note |

The next card checks ending the session. Separate cards check rapid double-press, app-side start/stop,
and the key used from another profile while another app is frontmost. A version/configuration change
invalidates old sign-off for affected cases rather than silently carrying green results forward.

Save progress and resume later; filter failed or untested cases; retest selected cases. Offer a short
smoke pass for frequent changes and a full pass covering both modes, profiles and optional actions.
Use a dedicated test chat/workspace for workflow Send and approval checks. Start with owner-entered
observations; optional future plugin diagnostics should record action IDs, outcome codes and timing,
not automatically collect conversations, audio or clipboard contents.

## Reports and implementation order

Export a readable HTML/Markdown report and machine-readable JSON with separate columns for
automated behavior, fixture-app integration, package verification and owner live acceptance. A
posted shortcut or successful helper exit is not itself a live app success. A release is ready only
when its required automated checks and required live cases pass; exceptions/skips stay explicit.

Implemented repository locations:

```text
tests/desktop/commands.json          shared catalog and scenarios
tests/desktop/DesktopCommandRig.cs   production-handler test rig
tests/desktop/fixture-app/           macOS helper integration target
tools/desktop-test/                  runner, local checklist and report export
artifacts/desktop-tests/<run-id>/    local results, ignored by git
```

Implementation order used:

1. Wire the shortcut test into the existing runner, add the exhaustive catalog, and generate an
   initial coverage report and resumable manual checklist from it.
2. Add the command/face seam and missing scenarios, starting with Voice Chat, Voice Draft, composer
   delivery and adaptive mode changes, then cover every remaining command parameter.
3. Add compiled-helper fixture tests and optional audio-file inference; connect all results to the
   same report. Preserve the existing package gate.

Completion criterion: every command/parameter/mode is accounted for, each advertised behavior has
an automated scenario or an explicit live-only case, and every hardware result identifies the
exact build tested. No production changes or reinstall are needed merely to collect this baseline.
